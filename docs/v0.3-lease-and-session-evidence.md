## 1. LEASE_CONFLICT reproduction (R00.1)

Reproduced offline with the real `registerAgent` tool layer against a throwaway project in the OS temp directory (`C:\Users\30502\AppData\Local\Temp\dsh-r00-lease-repro`). No live database was touched.

Sequence and observed facts:

| Step | Observation |
|---|---|
| Session A `memory_start_task` | task created, `session.bound` event emitted |
| Session A `memory_commit` #1 | ok; store now holds `lease_owner=project-memory:session-A`, `lease_fence=1`, `lease_expires_at=now+300000`; events `lease.acquired` then `checkpoint.created` |
| Session A disposed (`agent/disposed`) | lease **survives dispose** (remaining 300 s). `AgentMemoryBinding.close()` only marks pending tool operations unknown; it never releases the lease and there is no `lease.released` event |
| Session B (new SessionId, same project) `memory_commit` #1 | rejected `LEASE_CONFLICT` with `owner=project-memory:session-A`, `expiresAt` as epoch ms |
| Session B `memory_commit` #2 (immediately) | rejected identically; nothing between attempts changes the outcome |
| New agent instance reusing session A's id, commit | **succeeds** (same owner reacquires, fence 2) — the conflict is strictly the different-owner case |
| After rewinding `lease_expires_at` on the temp copy (TTL expiry simulation), session B commit | succeeds (fence 3) |

Event order per commit: `lease.acquired → checkpoint.created`; no release events exist anywhere. Conclusion: after any successful commit the task is locked against every *other* session for the full 300 s TTL, and resume-with-a-different-session-id (new conversation, fork — forks mint a new SessionId) fails twice in a row exactly as reported. Same-id resume cannot conflict.

Additional surface: the v0.2 panel flow (`claim`/`checkpoint` remotes) uses owner `project-memory-ui:<cwd>`, so a panel save can also collide with the agent owner of the same task. v0.2 `claim` wrote the bare session id as owner.

## 3. Harness session / Client workspace interface (R00.2, R00.3)

Verified against the installed `0.2.1-rc.3` sources (`dsh-agent`, `dsh-agent-loop`, `dsh-tools`, `dsh-api-session-controller`, `dsh-client-ui-session`):

- `agent/created` payload is `{ agent, source, signal? }`. `source` distinguishes fresh creation / **resume** / clear / compaction. The registry emits it via `ctx.serial` — plugins' async listeners are **awaited** before the agent starts work. The plugin currently ignores `source`.
- `agent/disposed` payload is `{ agent }`. Emitted synchronously, listener promises are **not awaited** (failures logged, contained). Lease release on dispose is therefore best-effort; crash still needs the TTL.
- `Agent.id` **is** the durable `SessionId` (branded type shared with the session log). `AgentRegistry.resume` reuses the persisted id and re-announces `agent/created`; **fork mints a new child id** (`SessionForkRequest` → `childId`) with a seeded prefix.
- There is **no stop hook**. Turn stopping is recorded as a `turn/end` session-log event, not a plugin event, and cannot be awaited by plugins. `tools/pre-execute` is a waterfall (awaited, `next()` composes); `tools/result` observers are contained.
- Client side: `ctx.uiSession` provides `session` / `session-maybe` **slot scopes**. Standard props include `SessionMaybeStandardProps.sessionId: SessionId | undefined` (absent on the welcome page), `useSessions` (full list; each `SessionSummary` carries `sessionId`, `cwd`, `agentAvailable`, `running`, `blank`), and `useSession`. Session-scoped slots can also receive `inject: (sessionId) => props` (trajectory pattern). So the Client **can** know its own window's session id — the dev.3 "single active agent" fallback is not the ceiling.
- Host side: `ctx.remote.session.list` exposes the same summaries to any Client; `workingDirectory.ensure(agent, signal)` remains the per-agent confirmed-directory source.

### Defect found and fixed while writing the integration test

`ProjectMemoryRemoteService.workspace(request = {})` — the default parameter made the function's arity 0, so the typert gateway derived a **zero-argument wire signature** and every real client call failed with `gateway/signature-invalid`. Fixed by `workspace(request)` + `request ??= {}` (`src/service.js`). This also means the dev.3 workspace feature had never actually worked across a real gateway — the offline tests never exercised the wire path for it.

New integration test: `test/session-interface.test.js` — real Registry/Gateway/Client loopback; asserts per-session `workspace({session_id})` resolution, `WORKSPACE_SELECTION_REQUIRED` with two live agents and the candidate list, `WORKSPACE_UNAVAILABLE` for unknown ids, and that `agent/disposed` withdraws exactly that session's candidate.

## 4. API gaps recorded for R01/R02/R05

1. `memory_commit` cannot proceed while any other owner's lease is live: no `lease_status` query, no readable retry time (only epoch ms), no deferred queue for independent appends, no lease release on dispose.
2. Commit's idempotency key defaults to `commit:<sessionId>:<task>:<version>`; a resumed session with a new id that replays the same logical commit writes a second checkpoint (no cross-session dedupe) — acceptable, but relevant when designing queue flush.
3. The panel's v0.2 `bootstrap/claim/checkpoint` remotes bypass session bindings entirely (UI owner per cwd); R02 must migrate the panel to `startTask/useTask/listTasks/setTaskState/commit`.
4. Client `client.js` never passes `session_id` to the workspace remote; the single-candidate heuristic must be replaced by session-scoped slot props (`sessionId` standard prop) once the slot scope provides it — real Desktop composition verified only in R05.
5. `agent/created`'s `source` field is available but unused; resume-vs-fresh distinction belongs in R01 lease strategy (e.g. same-id resume may reacquire immediately).
6. No plugin-visible stop/turn-end hook exists, so "waiting for the other session" can only be handled by lease TTL, dispose release, or user-driven retry — not by listening for the other agent's turn completion.

## 5. R01 implementation record (2026-10-25, `0.3.0-dev.4`)

Implemented after the evidence above, all offline with `os.tmpdir()` projects:

- Schema **v3** adds `deferred_commits`; every marker upgrade (v1 or v2) now takes a `memory.sqlite.v<V>-backup` recovery copy first (`test/r01-lease.test.js` covers the v2→v3 path with a real v2 database).
- `memory_commit` holds a short (60 s), implicitly renewable lease. Strict fields (`state`, `next_action`, `blockers`) under a foreign lease fail readably: `LEASE_CONFLICT` with `heldBy: 'other-session'`, `retryAfterSeconds`, `canRetryAt` (ISO), and the requested strict diff — never owner/fence in the error body. When the foreign lease expires within 2 s, one backed-off retry runs before failing.
- Append-only commits (`progress`, `evidence_refs`, `acceptance_updates` with no strict fields) enqueue into `deferred_commits` (`status=queued`) and return `synced: false` without claiming a checkpoint. Repeated identical defers deduplicate.
- The next lease holder flushes the queue at most once per commit: each item replays as its own append-only checkpoint (`deferredFlush` marker, `deferred:<id>` idempotency); a contract-revision mismatch on acceptance observations marks the item `conflict` with a reason instead of dropping it (`needsReview` in the commit result).
- Normal `agent/disposed` releases this session's own lease (`lease.released` event); crashes still fall back to the TTL. Same-id resume reacquires immediately (R00 §1).
- New agent tools `memory_lease_status`, `memory_deferred_list`, `memory_deferred_discard`; new panel Remotes `leaseStatus`, `deferred`, `discardDeferred`; `snapshot` now carries `leaseStatus` (UI-safe fields + diagnostics), `deferredCounts`, and `deferredItems`.
- Panel: persistent save-state bar (`已保存于…`/`正在保存`/`等待另一会话（约 N 秒）`/`未保存—可重试`), retry-save and discard-draft actions, deferred-draft list with `排队中`/`需要复核` badges, Chinese per-code error copy with relative timestamps, and a diagnostics-only disclosure for code/owner/ISO/fence. Verified by a stateful smoke render (lease-held, queued+conflict drafts, and saved states).
- `npm run check` and 39/39 tests pass (8 new R01 tests + the real-gateway session-interface test). Still pending: real-profile A/B session validation (R06 gate) and R02–R06.

## 6. R02 implementation record (2026-10-25, `0.3.0-dev.4`)

- Binding invalidation: `resolveTask` now reads the raw `session_bindings` row; a binding whose task reached `completed`/`archived` resolves to `selectionRequired` with the remaining open candidates (`source: 'invalidated-binding'`) and never auto-adopts the sole remaining open task. `test/r02-tasks.test.js` covers distinct bindings, third-session selection, completion not touching another session's binding, archived bindings, and that `listTasks` ordering is display-only.
- Panel v0.3 flow: new Remotes `startTask`/`useTask`/`listTasks`/`setTaskState`/`commit` (`requireSessionId` fails closed with `SESSION_REQUIRED`); `snapshot` accepts `session_id` for binding-aware reads while the legacy panel owner remains the lease viewer. The real-gateway test `session-bound task flow crosses the gateway with explicit session ids` drives startTask → binding-aware snapshots → third-session `TASK_SELECTION_REQUIRED` → token-free commit → complete → invalidated binding, all through the wire.
- Client: the panel prefers the slot-scoped `sessionId` standard prop (R00 §3) and falls back to the Host workspace remote's sole-candidate answer only when unscoped; the task view now lists open tasks with 选择/暂停/继续/完成/归档, a 新建任务 form bound to the current session, a v0.3 commit form, and a selection banner that names the candidates instead of guessing.
- Full suite: 44/44 (`npm test` includes `test/r02-tasks.test.js` and both real-gateway tests).
